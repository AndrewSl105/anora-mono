# Decisions

Deviations from docs/SPEC.md, one line of reasoning each.

- 2026-10-14 — All eight phases built in one pass without stopping between phases: the owner explicitly waived the per-phase stop ("go for all phases").
- Runner `seq` continues across runs of a task (read from `.anora/events.jsonl`), so replay is a simple `seq > last persisted` filter per task.
- On exit 4 (limit exceeded) the runner commits work in progress before exiting, so a follow-up run continues from it instead of losing it.
- Runner `task_id` accepts a string or a number (tasks use bigserial ids); the Go side always sends a string.
- An `answer` that arrives before its `question` is buffered, so a whole session can be piped from a file.
- Runner image builds TypeScript in a `node:24-bookworm-slim` stage and runs on `mcr.microsoft.com/playwright:v1.64.1-noble`; the image's existing uid 1000 user is replaced by `runner`.
- Go module path: `github.com/andrewsl105/anora-runner`.
- Docker client is `github.com/moby/moby/client`: the spec's `github.com/docker/docker/client` path is deprecated in favour of the new moby module.
- GitHub App auth uses `github.com/bradleyfalzon/ghinstallation/v2` (the spec's `bradleyfitz` is a typo) and `google/go-github/v92` (latest major).
- `tasks` gets two extra columns, `paused_at` (for `SIDECAR_IDLE_TTL`) and `cleaned_at` (workspace cleanup bookkeeping); `runs` gets `created_at`.
- A queued run is a `runs` row with `started_at IS NULL`. Create, resume, follow-up and retry all insert one and set the task to `queued`, so the scheduler has a single path.
- The API exposes `max_duration` as `max_duration_sec` (integer seconds) instead of a Postgres interval string.
- Session cookie value is `<id>.<HMAC-SHA256(SESSION_SECRET, id)>`, so forged cookies are rejected before a DB lookup.
- `COOKIE_INSECURE=true` (local development only) drops the cookie's `Secure` flag so login works over plain http.
- Login rate limiting is in memory (single process). Client IP comes from `X-Forwarded-For` only when the direct peer is a private address.
- `PATCH /projects/{id}`: omitted fields are unchanged; `""` or `0` resets an override to the server default.
- Retry re-runs the original prompt as a fresh session (no resume) on the same branch.
- Answer delivered by the Mini App or web is recorded as `answered_via: "web"`; the bot records `telegram`.
- Runner (phase 5): permissions use `permissionMode: "acceptEdits"` plus `allowedTools` for the nine listed tools, so nothing ever prompts; `AskUserQuestion` is available via `tools` but not pre-approved, so it always reaches `canUseTool`, which turns it into `question` events and returns the answers as `updatedInput.answers`. The SDK warns on stderr that `canUseTool` is shadowed for the pre-approved tools; that is intended, because the policy runs in a `PreToolUse` hook, which fires for every call regardless of approval.
- Runner policy also denies environment dumps (`env`, `printenv`, `export -p`, `set`, …) and any Bash command mentioning `CLAUDE_CODE_OAUTH_TOKEN`/`ANTHROPIC_API_KEY`, because Bash inherits the auth env. Residual risk: a program can still read its own env (e.g. `node -e 'process.env'`); the backend's secrets scan before push is the backstop.
- Runner policy recognises git/docker only in command position (after env assignments and wrappers such as sudo/xargs/timeout, and inside `bash -c`/`eval`), so `grep docker` or `grep "git push"` stay allowed.
- Runner relies on the SDK's `maxBudgetUsd` for the budget limit instead of comparing reported cost, because the reported total of a resumed session includes earlier runs.
- Runner `settingSources: ["project"]` loads the repo's `CLAUDE.md` and `.claude/settings.json`; user/local settings are not loaded.
- The Claude Code binary comes from the SDK's per-platform optional dependency (`@anthropic-ai/claude-agent-sdk-linux-<arch>`), installed by `npm ci` in the build stage for the target platform; it runs on the Playwright noble image (verified `2.1.299` on arm64).
- Startup reconciliation lives in `internal/scheduler/reconcile.go` rather than `internal/maintenance/`, because it shares the scheduler's run supervision (attach, stream, exit handling); `maintenance/` keeps retention and cleanup.
- Heartbeat events are not persisted (they would dominate the events table); everything else from the runner is stored verbatim.
- On re-attach the backend attaches first and replays `events.jsonl` second; duplicates are dropped by `UNIQUE (run_id, seq)`.
- Runner containers are named `anora-agent-<task>` and run as `1000:1000`; sidecars get the network alias `postgres` / `redis` and are reached as `DATABASE_URL=postgres://app:<random>@postgres:5432/app` and `REDIS_URL=redis://redis:6379/0`. The Postgres password is recovered from the sidecar's env when it is reused.
- `waiting_input` holds a scheduler slot like `running`, because its container is alive.
- A resumed run (after a question timeout) gets the answer restated in its prompt, and the backend also writes an `answer` for the original question id so the fake runner's scripted re-ask is satisfied.
- Exit 4 (limit) with new commits still pushes and opens/updates the PR (status `pr_open`, reason = the limit message); with nothing to push the task fails with the limit message.
- Without a GitHub App (`Publisher` nil) a run with commits ends `completed` with reason "committed locally"; this is how phase 3 and local development work.
- Cleanup (container/network removal) happens before the terminal status is written, so observers never see a finished task with live containers.
- A run's own cost is the runner's cumulative session cost minus what earlier runs of the same session (since the last `initial`/`retry`) already recorded.
- Installation tokens are minted with `repositories: [<name>]`, so each token reaches exactly one repo; git gets it as a one-command `-c http.extraHeader=Authorization: Basic …` and git stderr is redacted before logging.
- Diff validation fails closed: if the secrets scanner is missing or errors, the push is rejected. `SECRETS_SCAN=off` exists for local development only.
- gitleaks runs as `gitleaks git --log-opts origin/<base>..HEAD --redact`; only `file:line rule` of each finding reaches logs, events and the task reason.
- Before creating a PR the publisher looks for an open PR on the branch, so a crash between push and PR creation does not open a duplicate.
- CI status: `requested`/`in_progress` → `pending`; a `failure` sticks until the next push starts new checks, so a later green suite cannot hide a red one.
- A merged or closed PR completes the task and removes its containers; `OnCIFailed` is a logged no-op hook for future auto-fixing.
- Docker integration tests must run with `go test -p 1`: startup reconciliation correctly removes containers of tasks unknown to its database, which includes another test package's tasks.
- Migration 00002 adds `projects.telegram_chat_id` and `tasks.telegram_chat_id/thread_id/message_id`: a bound topic needs its forum chat id, and each task's status message must stay editable across restarts.
- Telegram messages use parse mode HTML; user text is cut before escaping, and every message is clamped below 4096 characters.
- A task's Telegram messages go to the chat/topic it was created from, else the project's bound topic, else the owner's private chat.
- "Open in app" is a `web_app` button in the private chat; in groups (where `web_app` buttons are not allowed) it is a `TELEGRAM_MINIAPP_LINK?startapp=task_<id>` deep link if configured, else a plain link to `WEB_APP_URL/tasks/<id>`.
- Failed and cancelled tasks also get a Retry button; question option buttons carry `ans|<question id>|<index>` (64-byte callback limit).
- Status events are attached to the task snapshot they produced (`Task.StatusEvent`), so publishing a task change also publishes its timeline event to WebSocket clients and the bot.
- Maintenance runs every 10 minutes. Event retention deletes only runner events (`seq` set) of terminal tasks, so each timeline keeps its status, PR and CI history. `WORKSPACE_RETENTION` (default 7 days) is configurable.
- Idle sidecars are removed for tasks in `paused` **or** `pr_open` after `SIDECAR_IDLE_TTL`: a PR can stay open for days, and a follow-up run recreates the sidecars anyway.
- `/metrics` answers only direct requests from private or loopback addresses without `X-Forwarded-For`, so the reverse proxy cannot expose it. `anora_tasks`, `anora_queue_length` and `anora_cost_usd_total` are read from Postgres at scrape time.
- The service image is `debian:bookworm-slim` with git, ca-certificates and gitleaks 8.30.1 (downloaded for `TARGETARCH`), running as uid 1000. `ENTRYPOINT ["anora"]`, `CMD ["serve"]`, so `docker run … hash-password` works.
- Images are built for linux/amd64 only (the target VPS). CI builds the runner image to run the Docker integration tests with the fake runner.
- Compose: `docker-socket-proxy` is pinned to `v0.5.0` with `CONTAINERS, ALLOW_START, ALLOW_STOP, ALLOW_RESTARTS, NETWORKS, VOLUMES, IMAGES, POST` enabled and `EXEC`/`BUILD` disabled. The `internal` network is `internal: true` (no egress); Anora Runner reaches GitHub and Telegram through `proxy`. `DATABASE_URL` is assembled from `PG_PASSWORD` in the compose file.
- Workflow actions are pinned to current majors (checkout/setup-go/setup-node v7, buildx/login v4, build-push v7, golangci-lint-action v9 with golangci-lint v2.14.0, appleboy/ssh-action v1.2.5).
- **Interrupt deviates from "stop the current turn, keep the session"**: the runner interrupts the turn, and the run then ends as `done` ("Interrupted by the user.") with what was committed, and pushes/updates the PR like any finished run. The session is kept: continue with a follow-up message (a new run resuming the same session).
- **A run handles one prompt**: the runner closes its input after the first turn's result, so a `message` injected after that point (the API already answered `delivery: "injected"`) is lost. Send it again as a follow-up once the run has finished.
- Runner output streams can be cut by the Docker socket proxy (HAProxy `timeout client/server 10m`) while a run waits for an answer; the scheduler re-attaches when the stream ends but the container still runs, and always replays `events.jsonl` before applying an exit.
- A runner exit is applied only while the task is still `running`/`waiting_input`; if the owner has already moved the task on (e.g. cancel then retry), the old run's exit leaves the new run alone.
- `RUNNER_USER` (default `1000:1000`) sets the runner containers' uid:gid; tests set it to the host user so Linux CI can share workspaces with the test process.
- `GET /tasks/{id}/events?before_id=` pages backwards, newest first; `before_id=0` means "from the newest" so the client can open a long timeline at its end without knowing an id. `cursor` stays an alias of `after_id`, so a backward `next_cursor` goes back as `before_id`; mixing directions is `400`.

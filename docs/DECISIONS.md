# Decisions

Deviations from the specs (`docs/SPEC-server.md` for server and agent, `docs/SPEC-web.md` for web), one line of reasoning each. Older lines keep the names they had in the separate repositories (fleetpocket-runner = server + agent, fleetpocket-client = web, "runner" = the agent).

## Monorepo

- 2026-10-15 — fleetpocket-runner and fleetpocket-client merged into this repository with their history: `git filter-repo` rewrote paths in each repository (Go service → `server/`, `runner/` → `agent/`, client → `web/`, shared docs and `deploy/` at the root), then both histories were merged, so `git log -- <path>` and `git blame` reach back to the first commits. Both were imported from their `integration` branches (the fleetpocket-runner one includes the unmerged `client-api-gaps`).

- Go module `github.com/andrewsl105/fleetpocket/server`; images `fleetpocket-server` (was `fleetpocket-runner`), `fleetpocket-agent`, `fleetpocket-web` (was `fleetpocket-client`). `RUNNER_IMAGE` keeps its default `ghcr.io/andrewsl105/fleetpocket-agent:latest` (the agent image name did not change); the variable name stays for compatibility with existing `.env` files. The agent identifies itself to the SDK as `fleetpocket-agent/<version>`.
- One copy of the contract: `docs/openapi.yaml`, `docs/API.md`, `docs/PROTOCOL.md`; `web` generates `src/api/schema.ts` from `../docs/openapi.yaml`, and the server's OpenAPI test reads the same file. The specs stay as written (`SPEC-server.md` still says "fleetpocket-runner"); this file records where the code differs.
- Compose services are named `caddy`, `web`, `server`, `postgres`, `docker-proxy` with no fixed container names (`docker compose exec <service>`), project `name: fleetpocket`. One network for the stack (`stack`: caddy, web, server) plus `internal` (postgres, docker-proxy, server) without egress.
- One release workflow replaces the two per-repository ones: it builds only images whose directory changed (`dorny/paths-filter@v4`; `workflow_dispatch` builds all), copies `deploy/docker-compose.deploy.yml` and `deploy/Caddyfile` with `appleboy/scp-action@v1.0.0`, pulls the changed images plus always `fleetpocket-agent`, runs `docker compose up -d` and `caddy reload` (the Caddyfile is a bind mount, so `up -d` would not pick up a change). The shared deploy lock of the two-repository setup is no longer needed: one workflow with a `concurrency` group.
- CI: path-filtered jobs; `agent/**` also runs the server job (its integration tests start the fake agent image), `docs/openapi.yaml` runs server (OpenAPI test) and web (schema check). The web job also runs the mock-mode Playwright tests.
- Root `Makefile` (GNU Make 3.81, the macOS default): `dev`, `dev-setup`, `test`, `lint`, `build`, `gen-api`, `e2e`, `e2e-real`.

## Server

- 2026-10-14 — All eight phases built in one pass without stopping between phases: the owner explicitly waived the per-phase stop ("go for all phases").
- Go module path: `github.com/andrewsl105/fleetpocket-runner` (now `github.com/andrewsl105/fleetpocket/server`, see Monorepo).
- Docker client is `github.com/moby/moby/client`: the spec's `github.com/docker/docker/client` path is deprecated in favour of the new moby module.
- GitHub App auth uses `github.com/bradleyfalzon/ghinstallation/v2` (the spec's `bradleyfitz` is a typo) and `google/go-github/v92` (latest major).
- `tasks` gets two extra columns, `paused_at` (for `SIDECAR_IDLE_TTL`) and `cleaned_at` (workspace cleanup bookkeeping); `runs` gets `created_at`.
- A queued run is a `runs` row with `started_at IS NULL`. Create, resume, follow-up and retry all insert one and set the task to `queued`, so the scheduler has a single path.
- The API exposes `max_duration` as `max_duration_sec` (integer seconds) instead of a Postgres interval string.
- Session cookie value is `<id>.<HMAC-SHA256(SESSION_SECRET, id)>`, so forged cookies are rejected before a DB lookup.
- `COOKIE_INSECURE=true` (local development only) drops the cookie's `Secure` flag so login works over plain http.
- Login rate limiting is in memory (single process). Client IP comes from `X-Forwarded-For` only when the direct peer is a private address.
- `PATCH /projects/{id}`: omitted fields are unchanged; `""` or `0` resets an override to the server default.
- Retry re-runs the original prompt as a fresh session (no resume) on the same branch.
- Answer delivered by the Mini App or web is recorded as `answered_via: "web"`; the bot records `telegram`.
- Startup reconciliation lives in `internal/scheduler/reconcile.go` rather than `internal/maintenance/`, because it shares the scheduler's run supervision (attach, stream, exit handling); `maintenance/` keeps retention and cleanup.
- Heartbeat events are not persisted (they would dominate the events table); everything else from the runner is stored verbatim.
- On re-attach the backend attaches first and replays `events.jsonl` second; duplicates are dropped by `UNIQUE (run_id, seq)`.
- Runner containers are named `fleetpocket-agent-<task>` and run as `1000:1000`; sidecars get the network alias `postgres` / `redis` and are reached as `DATABASE_URL=postgres://app:<random>@postgres:5432/app` and `REDIS_URL=redis://redis:6379/0`. The Postgres password is recovered from the sidecar's env when it is reused.
- `waiting_input` holds a scheduler slot like `running`, because its container is alive.
- A resumed run (after a question timeout) gets the answer restated in its prompt, and the backend also writes an `answer` for the original question id so the fake runner's scripted re-ask is satisfied.
- Exit 4 (limit) with new commits still pushes and opens/updates the PR (status `pr_open`, reason = the limit message); with nothing to push the task fails with the limit message.
- Without a GitHub App (`Publisher` nil) a run with commits ends `completed` with reason "committed locally"; this is how phase 3 and local development work.
- Cleanup (container/network removal) happens before the terminal status is written, so observers never see a finished task with live containers.
- A run's own cost is the runner's cumulative session cost minus what earlier runs of the same session (since the last `initial`/`retry`) already recorded.
- Installation tokens are minted with `repositories: [<name>]`, so each token reaches exactly one repo; git gets it as a one-command `-c http.extraHeader=Authorization: Basic …` and git stderr is redacted before logging.
- Diff validation fails closed: if the secrets scanner is missing or errors, the push is rejected. `SECRETS_SCAN=off` exists for local development only.
- gitleaks runs as `gitleaks git --log-opts origin/<base>..HEAD --redact`; only `file:line rule` of each finding reaches logs, events and the task reason.
- Before creating a PR the publisher looks for an open PR on the branch, so a crash between push and PR creation does not open a duplicate.
- CI status: `requested`/`in_progress` → `pending`; a `failure` sticks until the next push starts new checks, so a later green suite cannot hide a red one.
- A merged or closed PR completes the task and removes its containers; `OnCIFailed` is a logged no-op hook for future auto-fixing.
- Docker integration tests must run with `go test -p 1`: startup reconciliation correctly removes containers of tasks unknown to its database, which includes another test package's tasks.
- Migration 00002 adds `projects.telegram_chat_id` and `tasks.telegram_chat_id/thread_id/message_id`: a bound topic needs its forum chat id, and each task's status message must stay editable across restarts.
- Telegram messages use parse mode HTML; user text is cut before escaping, and every message is clamped below 4096 characters.
- A task's Telegram messages go to the chat/topic it was created from, else the project's bound topic, else the owner's private chat.
- "Open in app" is a `web_app` button in the private chat; in groups (where `web_app` buttons are not allowed) it is a `TELEGRAM_MINIAPP_LINK?startapp=task_<id>` deep link if configured, else a plain link to `WEB_APP_URL/tasks/<id>`.
- Failed and cancelled tasks also get a Retry button; question option buttons carry `ans|<question id>|<index>` (64-byte callback limit).
- Status events are attached to the task snapshot they produced (`Task.StatusEvent`), so publishing a task change also publishes its timeline event to WebSocket clients and the bot.
- Maintenance runs every 10 minutes. Event retention deletes only runner events (`seq` set) of terminal tasks, so each timeline keeps its status, PR and CI history. `WORKSPACE_RETENTION` (default 7 days) is configurable.
- Idle sidecars are removed for tasks in `paused` **or** `pr_open` after `SIDECAR_IDLE_TTL`: a PR can stay open for days, and a follow-up run recreates the sidecars anyway.
- `/metrics` answers only direct requests from private or loopback addresses without `X-Forwarded-For`, so the reverse proxy cannot expose it. `fleetpocket_tasks`, `fleetpocket_queue_length` and `fleetpocket_cost_usd_total` are read from Postgres at scrape time.
- The service image is `debian:bookworm-slim` with git, ca-certificates and gitleaks 8.30.1 (downloaded for `TARGETARCH`), running as uid 1000. `ENTRYPOINT ["fleetpocket"]`, `CMD ["serve"]`, so `docker run … hash-password` works.
- **Interrupt deviates from "stop the current turn, keep the session"**: the runner interrupts the turn, and the run then ends as `done` ("Interrupted by the user.") with what was committed, and pushes/updates the PR like any finished run. The session is kept: continue with a follow-up message (a new run resuming the same session).
- **A run handles one prompt; messages sent while a run is active are queued, not injected.** The runner closes its input after the first turn's result, so injected text could be lost while the API claimed `delivery: "injected"`. The backend no longer sends `message` to runners: `POST …/message` in `queued`/`preparing`/`running`/`waiting_input`/`pushing` appends to `tasks.queued_message` (migration 00004) and answers `delivery: "queued"`. Making injection reliable in the runner was rejected: after a `result` the backend cannot know whether late text was consumed, and the SDK gives no delivery acknowledgement.
- The queue is drained in the same transaction as the status change that ends the run (`setStatusTx`): `pr_open`/`completed` → a `followup` run, `paused` → a `resume` run, so no second code path can requeue over it. `failed`/`cancelled` drop it with a `message_dropped {text, reason}` event so the owner sees what was not sent. `pushing` queues too, because a run moves to `pushing` right after `done` and a message sent a second late would otherwise get `409`.
- An answer that arrives while a runner is exiting on a question timeout is added to the same queue (as the restated answer) before the task moves to `paused`, so the answer and any queued message become one resume run.
- `Task.StatusEvent` became `StatusEvents`: a drained status change writes two status events (`pr_open`, then `queued`), and both are published.
- Runner output streams can be cut by the Docker socket proxy (HAProxy `timeout client/server 10m`) while a run waits for an answer; the scheduler re-attaches when the stream ends but the container still runs, and always replays `events.jsonl` before applying an exit.
- A runner exit is applied only while the task is still `running`/`waiting_input`; if the owner has already moved the task on (e.g. cancel then retry), the old run's exit leaves the new run alone.
- `RUNNER_USER` (default `1000:1000`) sets the runner containers' uid:gid; tests set it to the host user so Linux CI can share workspaces with the test process.
- `GET /tasks/{id}/events?before_id=` pages backwards, newest first; `before_id=0` means "from the newest" so the client can open a long timeline at its end without knowing an id. `cursor` stays an alias of `after_id`, so a backward `next_cursor` goes back as `before_id`; mixing directions is `400`.
- Migration 00003 adds `runs.turns`, `tasks.turns`, `tasks.last_activity` and `tasks.last_activity_at`, denormalised on the row so the list view needs no event queries; it backfills them from the events retention has kept.
- A run's `turns` is its last `usage.turns`, with no session baseline (unlike cost): the SDK's `num_turns` counts round-trips within one query and restarts on resume (checked in the bundled CLI, whose schema describes it as "model round-trips within one turn").
- `last_activity` is set in the same transaction as every status change (`<status>` or `<status>: <reason>`) and on each newly stored `tool_use` (replays don't overwrite it); first line only, cut to 120 runes.
- `tool_use` and `usage` events now publish a task snapshot, so `scope: "tasks"` subscribers get live `turns`/`last_activity`. The Telegram bot already throttles status edits per task (`EditInterval`), so this adds no Telegram traffic.
- `GET /tasks/{id}/runs` returns the full `Run` object (also `task_id`, `container_id`, `last_seq`, the same shape as `latest_run`) oldest first, including a queued run with `started_at: null`; it follows the list convention (`limit`/`cursor`) although a task rarely has more than a handful of runs.
- `PATCH /projects/{id}/repositories/{repoId}`: un-defaulting the default repo is `409 conflict`, because `POST /tasks` without `repository_id` needs a default; changing `base_branch` is `409 in_use` while unfinished tasks (anything but `completed`/`failed`/`cancelled`, including `pr_open`) use the repo, because their push, diff and PR base would silently change mid-task.
- `base_branch` is validated as a plain branch name on add and update (it reaches `git clone --branch`, so an option-like value such as `--upload-pack=…` must be rejected).
- OpenAPI `Event` is a `oneOf` of one schema per event type with a `discriminator` on the envelope's `type`, because backend payloads carry no `type` of their own. Runner variants require `run_id`/`seq` as integers; backend variants have `seq: null`. Verified with the client's `openapi-typescript` 7.13: `Event` becomes a union that narrows on `type`. A runnermgr test fails if a runner event type is missing from the mapping.
- The backend event names stay as emitted and stored (`status`, `ci`, `pr_opened`, …); the client's request called them `status_changed` and `ci_status`, but renaming would break stored timelines and existing consumers (the Telegram bot).
- Runner error `code` stays a plain string in the schema (documented values listed), so a new runner error code does not break generated clients.
- **Telegram Web fallback: bearer token + WebSocket ticket.** Telegram Web K and A (`web.telegram.org`, `webk.`/`weba.telegram.org`) embed the Mini App in a cross-site iframe, where `SameSite=Lax` cookies are neither sent nor stored (RFC 6265bis "site for cookies"); Telegram's native apps load it top-level, so the cookie works there. `SameSite=None; Partitioned` was rejected: it needs Safari 26.2+, and Safari/Firefox partition or block it anyway. `POST /auth/telegram` therefore also returns the signed session value as `token`; `Authorization: Bearer` is accepted only for `telegram` sessions, so a stolen browser cookie cannot be replayed as a header and browser logins stay cookie-only.
- WebSocket handshakes cannot carry headers, so `POST /api/v1/ws/ticket` issues a 30-second, single-use ticket bound to the session (in memory; a restart only forces a new ticket), redeemed by `GET /api/v1/ws?ticket=`. The session is re-checked at redeem time. Tickets work for any session kind; only bearer clients need them.
- **Image attachments (2026-10-16).** Limits set by the owner: 40 MB per file (the request said 10 MB), at most 10 files and 100 MB per request. Images over 50 megapixels are rejected before decoding (a 50 MP image is 200 MB as RGBA), and decoding runs one image at a time, so concurrent uploads cannot multiply that peak on the 8 GB host.
- The type is detected from the first bytes (PNG, JPEG, GIF, WebP); the file name and the declared Content-Type are ignored. JPEG, PNG and GIF are decoded and re-encoded, which drops EXIF, XMP, text chunks and comments; JPEG is re-encoded at quality 92 after applying its EXIF orientation to the pixels, because re-encoding drops the orientation tag and phone photos would turn sideways.
- WebP is not re-encoded (Go has no WebP encoder and cgo would complicate the image): the RIFF container is rewritten without its `EXIF` and `XMP ` chunks and the VP8X flags are cleared; the image data is copied byte for byte and then decoded as a check. A WebP's EXIF orientation is therefore dropped, not applied (rare outside cameras).
- Animated GIF and animated WebP are rejected: Claude Code's Read tool sends only one frame, so the agent would see something other than what the owner sent. A single-frame GIF is re-encoded with `gif.EncodeAll`, which writes no comment or application extensions.
- Thumbnails (longest side 480 px, JPEG over white) are made at upload time and stored in `<task>/.thumbs/`, so `?thumb=1` costs no decoding. The `.thumbs` folder is part of the task folder and therefore also visible to the agent; the prompt lists only the originals.
- `ATTACHMENTS_DIR` (default `/srv/fleetpocket/attachments`) must not contain `WORKSPACES_DIR` or lie inside it, so attachments never end up in a git workspace. Files are written to a temporary name and renamed; an upload holds a read lock while its rows and files are written, and a sweep (which removes files without a live row) takes the write lock, so it never deletes the file of an upload whose transaction has not committed yet.
- New backend event `created` (`{attachments}`), written for every new task right before its first `status`: the request asked for attachments "in the task-create event", and there was no such event. Old timelines simply have none. `message` events get `attachments` only when images were sent, so existing payloads keep their shape.
- An attachment's `run_id` names the run whose prompt carries it and is set when that run is queued: at creation (the initial run), for a message that starts a run right away, and when queued messages are drained into the next run. A message queued before the initial run starts therefore reaches the run that handles its text, not the initial run. A retry receives the creation's attachments again. Everything else still live is listed to the agent as earlier attachments.
- Multipart uploads are read part by part with their own body limit (100 MB + 1 MB for fields); the 1 MB JSON limit stays for every other request. Unknown multipart fields are `400` like unknown JSON fields; files may be sent as `files[]` or `files`.
- `GET /tasks/{id}/attachments/{attachmentId}` answers `410 gone` for a removed attachment, so clients can show "image removed" instead of a broken image. Responses are `Cache-Control: private` with `nosniff` and a `sandbox` CSP.
- **Telegram task UX (2026-10-16).** Every task keeps one editable card; only questions, PRs, failures, CI failures and limits create notification messages, all as replies to the card. `telegram_task_messages` maps every task-related bot message back to its task and records whether its keyboard is live, so replies route consistently and state transitions can remove stale actions.
- Telegram callback data is only `c:<10-character opaque id>`; action, task/draft/question ids and values live in `telegram_callbacks` for 24 hours. This avoids leaking mutable identifiers into callbacks and makes the 64-byte limit structural rather than best-effort.
- Owner messages that are neither commands nor task replies merge into database-backed drafts for three seconds and expire after 24 hours. A bound topic wins as the project default; otherwise `telegram_chat_state` remembers the last confirmed project/repository in that chat and topic. Telegram file ids stay in the draft and images are downloaded, validated and metadata-stripped only after confirmation.
- Reply routing is message-based, not question-message-only: if the mapped task has an unanswered question the reply answers it, otherwise it uses the same `tasks.Message` queue/follow-up rules as REST. ForceReply prompts are persisted separately so restarts do not lose draft edits or custom question answers.
- `STT_PROVIDER=off|openai|whispercpp`. OpenAI uses the multipart `/v1/audio/transcriptions` endpoint with `gpt-transcribe`; whisper.cpp uses the sidecar's `/inference` endpoint with language auto-detection and requires the sidecar's `--convert` option for Telegram audio. Transcripts become editable draft text and are echoed before a voice task reply is delivered.
- Telegram currently documents 👀 as a standard reaction but not ✅/❌. The bot still attempts the requested received/delivered/error reactions; reaction API errors are metered and never prevent the underlying message from being handled.

## Agent

- Runner `seq` continues across runs of a task (read from `.fleetpocket/events.jsonl`), so replay is a simple `seq > last persisted` filter per task.
- On exit 4 (limit exceeded) the runner commits work in progress before exiting, so a follow-up run continues from it instead of losing it.
- Runner `task_id` accepts a string or a number (tasks use bigserial ids); the Go side always sends a string.
- An `answer` that arrives before its `question` is buffered, so a whole session can be piped from a file.
- Runner image builds TypeScript in a `node:24-bookworm-slim` stage and runs on `mcr.microsoft.com/playwright:v1.64.1-noble`; the image's existing uid 1000 user is replaced by `runner`.
- Runner (phase 5): permissions use `permissionMode: "acceptEdits"` plus `allowedTools` for the nine listed tools, so nothing ever prompts; `AskUserQuestion` is available via `tools` but not pre-approved, so it always reaches `canUseTool`, which turns it into `question` events and returns the answers as `updatedInput.answers`. The SDK warns on stderr that `canUseTool` is shadowed for the pre-approved tools; that is intended, because the policy runs in a `PreToolUse` hook, which fires for every call regardless of approval.
- Runner policy also denies environment dumps (`env`, `printenv`, `export -p`, `set`, …) and any Bash command mentioning `CLAUDE_CODE_OAUTH_TOKEN`/`ANTHROPIC_API_KEY`, because Bash inherits the auth env. Residual risk: a program can still read its own env (e.g. `node -e 'process.env'`); the backend's secrets scan before push is the backstop.
- Runner policy recognises git/docker only in command position (after env assignments and wrappers such as sudo/xargs/timeout, and inside `bash -c`/`eval`), so `grep docker` or `grep "git push"` stay allowed.
- Runner relies on the SDK's `maxBudgetUsd` for the budget limit instead of comparing reported cost, because the reported total of a resumed session includes earlier runs.
- Runner `settingSources: ["project"]` loads the repo's `CLAUDE.md` and `.claude/settings.json`; user/local settings are not loaded.
- The Claude Code binary comes from the SDK's per-platform optional dependency (`@anthropic-ai/claude-agent-sdk-linux-<arch>`), installed by `npm ci` in the build stage for the target platform; it runs on the Playwright noble image (verified `2.1.299` on arm64).
- Interrupt while a question is open: the fake runner now ends the run as `done` ("Interrupted by the user."), as a real session does, so local development and the integration tests exercise interrupt; before, it kept waiting for the answer and the client showed "stopping" indefinitely. The real runner's `canUseTool` stops waiting for the answer when the SDK aborts its `signal` (interrupt) instead of leaving the permission request pending.
- Attachment lifecycle: `completed` deletes the task's attachments in the same transaction as the status change (rows get `deleted_at`, files go right after through a hub subscriber); attachments of a queued message survive it, because the queue starts a follow-up run with them. **Cancelled tasks keep their attachments like failed ones** (the owner's choice; the request said delete on cancel) because `retry` works on cancelled tasks too; both lose them with the workspace (`WORKSPACE_RETENTION`). A queued message that is dropped loses its images. Every maintenance pass (and so every startup) also sweeps files without a live row and folders of tasks that no longer exist.
- Telegram images: an album (media group) arrives as one update per photo; the bot collects a group for 1.5 s after its latest photo and handles it as one message, led by the captioned photo, so it becomes one task, one draft update or one message to a task. The album delay is added to the three-second draft merge window, and every part gets its own received/delivered reaction. Images without text are not sent with a made-up prompt: a reply to a task gets a ForceReply prompt ("What should Claude do with the image(s)?") and the draft's Create button asks for the text first. The waiting file ids of such a prompt are kept in memory (24 h); after a restart the reply asks to send the images again with a caption, which avoids a table for a rare case. Image documents are admitted by image MIME type or a known image extension, then content-sniffed by the attachment validator. `/new` as a photo caption attaches the photo. Bot API `getFile` serves at most 20 MB, below the 40 MB upload limit.
- Telegram sends cards, drafts, commands, ForceReply prompts, transcript echoes and other routine UI messages silently. Only questions, opened PRs, task failures, CI failures and limit notifications opt into sound, matching the notification allow-list instead of relying on the chat's current defaults.
- Attachments reach the agent through the prompt, not a new stdin command: the `run` prompt ends with a block listing `/attachments/<id>.<ext>` paths (the stored run `input` stays the owner's text). The folder is a read-only bind mount added only when the task has live attachments, so Docker never creates a missing bind source as root; the SDK gets `additionalDirectories: ["/attachments"]` when it exists, so the Read tool may open files outside `cwd` (the bundled Claude Code reads png/jpg/jpeg/gif/webp and compresses images over the API limit itself, checked in SDK 0.3.299).
- The policy denies writes under `/attachments` for Write/Edit, Bash write commands, in-place edits and redirections, with a reason telling Claude to copy into the workspace instead; `cp`/`rsync`/`install` from `/attachments` into the workspace stay allowed. The `:ro` mount is the real guarantee (the integration test sees `EROFS`).
- 2026-10-20 — The policy denies WebFetch and `curl`/`wget` on claude.ai artifact and share links (`/public/artifacts/`, `/share/`, `/api/published_artifacts/`, `/api/chat_snapshots/`). The spec allows WebFetch, but those pages are rendered by JavaScript and their API sits behind a Cloudflare bot challenge, so a fetch only ever returns an empty app shell. The denial reason tells Claude to ask the owner to paste the content.
- 2026-10-19 — The owner can merge a `pr_open` task's PR from Fleetpocket (`POST /tasks/{id}/merge`, a web button, a Telegram "Merge" button with a confirm step), although the spec says they merge it themselves: the owner asked for it. It always squash-merges (title `<task title> (#n)`) and deletes the branch, as the owner chose; the task completes right away instead of waiting for the webhook, and the webhook skips its `pr_closed` event when the latest PR event already is that close (which also absorbs redeliveries). GitHub's refusal is `409 not_mergeable` with its message. The App's existing Contents and Pull requests write permissions cover both calls.

## Deployment and CI

- Images are built for linux/amd64 only (the target VPS). CI builds the runner image to run the Docker integration tests with the fake runner.
- 2026-10-18 — `ci.yml` no longer runs on pull requests (both specs say it does), only on pushes to `main` and `workflow_dispatch`: the owner does not want CI checks on the PRs Anora opens. A PR can still be checked by hand with "Run workflow" on its branch. Not applied yet: `ci.yml` still has `pull_request:`, because the GitHub App has no Workflows permission (DEPLOY.md step 5), so Anora cannot push changes to `.github/workflows/`; removing the trigger is a manual step.
- Compose: `docker-socket-proxy` is pinned to `v0.5.0` with `CONTAINERS, ALLOW_START, ALLOW_STOP, ALLOW_RESTARTS, NETWORKS, VOLUMES, IMAGES, POST` enabled and `EXEC`/`BUILD` disabled. The `internal` network is `internal: true` (no egress); Anora Runner reaches GitHub and Telegram through `proxy`. `DATABASE_URL` is assembled from `PG_PASSWORD` in the compose file.
- Workflow actions are pinned to current majors (checkout/setup-go/setup-node v7, buildx/login v4, build-push v7, golangci-lint-action v9 with golangci-lint v2.14.0, appleboy/ssh-action v1.2.5).
- `deploy/docker-compose.dev.yml` (local development): `fleetpocket` sits on the default network (egress for anonymous clones of public repos, published port) and on `internal: true` with Postgres and the socket proxy. Workspaces use `${PWD}/.dev/workspaces` on both sides of the bind mount, because `WORKSPACES_DIR` must be the same path on the host and in the container and `/srv` does not exist on macOS. A one-shot `agent` service builds `fleetpocket-agent:dev`, which Fleetpocket Runner never pulls. Credentials come from a gitignored `deploy/.env.dev`; `SECRETS_SCAN=off` because nothing is pushed.
- Dev compose only: `safe.directory=*` through `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0`/`GIT_CONFIG_VALUE_0`, because Docker Desktop's macOS file sharing intermittently reports another owner for bind-mounted workspaces and git then fails the task with "dubious ownership" (found running the client's e2e against the dev stack). Production on Linux keeps real uids and needs nothing.
- **Deployment on one server with Caddy in the compose file.** `docker-compose.deploy.yml` now also runs `fleetpocket-client` and `caddy` (`caddy:2.11.7-alpine`, ports 80/443 and 443/udp, volumes `caddy_data`/`caddy_config`); `deploy/Caddyfile` serves `{$FLEETPOCKET_DOMAIN}` with automatic HTTPS and routes `/api/*` (WebSocket included), `/webhooks/*`, `/healthz` to `fleetpocket:8080`, everything else to `fleetpocket-client:80`, and answers `/metrics*` with 404 (Fleetpocket Runner refuses proxied `/metrics` anyway; without the rule the path would reach the SPA fallback). Verified locally with `FLEETPOCKET_DOMAIN=localhost`: routing, CSP, Secure cookie over HTTPS, and the client's real-backend Playwright tests through Caddy.
- **The `proxy` network belongs to the compose file** (now named `stack`, see Monorepo) instead of being external: Caddy is now part of the stack, so nothing outside it joins the network, and a fresh server needs no `docker network create`. Nothing in the code refers to the network by name.
- *(Superseded by the monorepo's single release workflow, see Monorepo.)* **Release workflows deployed one service each** to the same `/srv/fleetpocket`: `pull <service>` + `up -d --no-deps <service>` (fleetpocket-runner: `fleetpocket`, plus `docker pull` of the agent image; fleetpocket-client: `fleetpocket-client`), inside `flock /srv/fleetpocket/.deploy.lock`, because GitHub `concurrency` groups do not span repositories. Deploy files are copied by hand (README), so a workflow never applies half of a compose change. `script_stop` was removed from appleboy/ssh-action v1.2.5 (it was silently ignored); the scripts use `set -e` as its README recommends.

### Backend contract gaps

- ~~Timeline paging is forward-only~~ — resolved with `before_id`: a timeline opens at its end (`before_id=0`, 200 newest, reversed) and older pages load on scroll-up or with "Load earlier activity"; prepending shifts the scroll position by the added height so rows on screen stay put. Reconnect catch-up stays forward (`after_id` = newest cached id), so the cache never has gaps.
- ~~No turns on Task~~ — resolved: the header shows `Task.turns`.
- ~~No "latest activity" on Task~~ — resolved: cards and the "Claude is working" line show `Task.last_activity` (CI status instead for `pr_open`), and the card time is `last_activity_at`.
- **No active-task count on Project.** Projects screen counts tasks from the Active list client-side (first 50 per page loaded).
- ~~Only `latest_run` in the API~~ — resolved: the Info tab reads `GET /tasks/{id}/runs` (with the run's own `cost_usd` and `turns`), refetched on `run_started`/`run_finished` pushes and status changes.
- ~~Repositories can't be edited~~ — resolved: base branch and default flag are edited in place (`PATCH …/repositories/{repoId}`). The default switch is disabled on the current default, because un-defaulting it is `409`; make another repo the default instead.
- ~~Event payloads are untyped~~ — resolved: OpenAPI `Event` is now a discriminated `oneOf`; `src/api/events.ts` only derives `EventOf<K>`/`PayloadOf<K>` from the generated union, and `buildTimeline` narrows with `switch (event.type)`.
- **One cast at the events response boundary.** openapi-fetch 0.17 (`openapi-typescript-helpers` 0.1.0, both latest) drops properties typed exactly `null` in its `Readable<T>` response transform (`NonNullable<null>` is `never`), so backend events lose `seq: null`; `asEvents()` in `hooks.ts` restores the generated `Event` type. The contract stays as is.
- **No OpenAPI examples.** MSW mocks (`src/mocks/`) use hand-written fixtures typed from `schema.ts` instead of generated examples. The mock db maintains `turns`, `last_activity` and per-run cost like the backend, serves `before_id`, `/runs` and repository PATCH, and seeds a 500-event task to exercise paging.
- **`Retry-After` on 429 is undocumented.** Used when present; otherwise the message uses the 15-minute window from API.md.
- **`X-Requested-With` is a required header parameter in OpenAPI**, so generated types demand it per call. Calls pass the shared `CSRF` constant and a middleware also sets it on every non-GET.

### Client choices

- **TypeScript 6.0, not 7.** typescript-eslint supports `<6.1`; openapi-typescript and msw peer ranges are overridden in package.json.
- **React Router** (not TanStack Router): simpler data-less routes; typed params are only `/tasks/:id` and `/projects/:id`.
- **Official `telegram-web-app.js` + `@types/telegram-web-app`**, wrapped in `src/telegram/`, not `@telegram-apps/sdk-react`: the spec's CSP already allows `https://telegram.org`, and it avoids a large SDK in the bundle.
- **One small hand-written CSS file** (`src/routes/tasks/diff.css`) overrides react-diff-view so long lines scroll instead of wrapping on phones.
- **CSP needs `style-src 'unsafe-inline'`**: React style attributes, Radix positioning, the virtualiser and sonner all set inline styles. Scripts stay `'self'` + telegram.org.
- **No brotli.** `nginx:alpine` has no brotli module; gzip only.
- **Failed filter includes `cancelled`**, since there is no separate tab for it.
- **401 handling lives in the custom `fetch`** passed to openapi-fetch (one shared re-auth for concurrent 401s, one retry), and error-to-`ApiError` conversion in `call()` rather than a response middleware.
- **Mock mode** (`VITE_MOCK=1`) uses MSW in the browser for REST and MSW's WebSocket interception for `/api/v1/ws`; `?tg=1` (and `&dark=1`) fakes the Telegram WebApp. Mock code is excluded from production builds.
- **Phases 1–5 were built and verified together** (one commit) because the user asked to run all phases without stopping; Phase 6 is a separate commit.

- **Image attachments.** An attach button (file input with `accept` listing PNG/JPEG/WebP/GIF, so phones offer camera and gallery and iOS hands over HEIC photos as JPEG), paste into the prompt or composer, and drag-and-drop on desktop. Previews with remove buttons; refused files are listed with the reason (type, 40 MB, 10 files, 100 MB together, mirroring the server). The text stays required, as on the server.
- **Uploads use XHR inside `api/client.ts`** (`uploadForm`): fetch reports no upload progress. It sends the CSRF header and the Telegram bearer token and re-authenticates once on 401 like the openapi-fetch client. In the composer test, MSW's XHR interceptor cannot read a jsdom `FormData`, so the test records `uploadForm` calls and `uploadForm` has its own unit test with a fake XHR.
- **Images are fetched as blobs through the API client and shown via object URLs**, because Telegram Web authenticates with a bearer token that an `<img src>` cannot send; the CSP's `img-src` gains `blob:`. The object URL is created in an effect on the `<img>` element and revoked on cleanup. A `410 gone` shows "Image removed". Thumbnails are sized from the stored width/height, so the virtualised timeline does not jump while they load.
- **The `created` event renders as a thumbnails-only bubble** ("N images attached to the task"); the prompt itself stays on the Info tab as before. Mock mode stores uploads in memory, serves them, emits `created`, removes a completed task's images and seeds one live and one removed image.

### Integration with the real backend

- **Messages while a run is active are queued, not injected** (backend change, see its DECISIONS). `composerMode` is `queue` in `queued`/`preparing`/`running`/`waiting_input`/`pushing` and `followup` in `paused`/`pr_open`/`completed`; the composer says the text starts the next run when this one ends. The optimistic bubble uses `delivery: "queued"` and keeps a "Queued" note until a `status: queued` event (the drained follow-up) arrives; `message_dropped` turns it into "Not sent: the task failed/was cancelled first". `Task.queued_message` is shown above the composer. Legacy `delivery: "injected"` bubbles say the text may not have reached Claude.
- **Interrupt ends the run.** The action is labelled "Stop and finish run"; after it is sent (an `interrupt` event since the last `run_started`) the working line says the run is ending and the action is hidden until the run finishes. A queued message then starts the next run, so "queue a message, then stop" redirects Claude.
- **Telegram mode authenticates with a bearer token, not only the cookie.** Telegram Web K/A (`web.telegram.org`, `webk.`/`weba.telegram.org`) embed the Mini App in a cross-site iframe, where the `SameSite=Lax` cookie is neither sent nor stored; native Telegram apps load it top-level. The `token` from `POST /auth/telegram` lives in a module variable in `api/client.ts` (never in storage; a reload logs in again with initData) and goes out as `Authorization: Bearer` on every call; a 401 re-auth retries with the new token. Browser mode stays cookie-only.
- **WebSocket tickets.** With a bearer token, every (re)connect first calls `POST /api/v1/ws/ticket` and opens `/api/v1/ws?ticket=…` (single use, 30 s); `RealtimeClient` accepts an async `url()` and ignores a ticket that arrives after `stop()`/suspend. A failed ticket request backs off like a dropped socket.
- **CSP checked against the real deployment.** API and WebSocket are same-origin behind Caddy, so `connect-src 'self' wss://$host` (nginx fills in the request host; the old bare `wss:` allowed any host). `frame-ancestors` lists the Telegram Web origins that embed Mini Apps (`web.telegram.org`, `webk.telegram.org`, `weba.telegram.org`, checked against the tweb/telegram-tt sources) instead of `*.telegram.org`; native apps load the page top-level, so they need no entry. `img-src 'self' data:` stays: Claude's markdown cannot pull remote images.
- **Playwright against the real backend** (`npm run e2e:real`, `E2E_BACKEND`): `e2e/real/` drives login (TOTP computed from `E2E_TOTP_SECRET`), project and task creation, the fake runner's question, a queued message with its follow-up run and deep links, and fails on any unexpected 4xx/5xx, console error or WebSocket error. The repository is added through the API because the dev backend has no GitHub App. Wrong credentials stay mock-only: the backend's 5-failures-per-15-minutes limit would lock repeated runs out. The Telegram Web case is reproduced with a real loopback page (`127.0.0.1`) framing the app (`localhost`): Chromium's Local Network Access checks block a routed, address-less parent from framing localhost.
- **Deploy**: the service, Caddy and the routing live in fleetpocket-runner's `docker-compose.deploy.yml`/`Caddyfile` (one server setup, documented there). `release.yml` restarts only `fleetpocket-client` (`up -d --no-deps`) under the shared `/srv/fleetpocket/.deploy.lock`, and uses `set -e` because appleboy/ssh-action v1.2.5 dropped `script_stop`.
